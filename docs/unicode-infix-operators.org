#+begin_abstract
Following on from the infix backtick operator. Backtick lets any /name/ sit in
infix position. The obvious next question is whether C++ could have
user-declared /symbolic/ operators: declare =operator⊞= like any other
function, and =5 ⊞ 7= calls it. Unicode has recently done the standards work
that makes the character-set question answerable, and the backtick project
already settled the precedence, associativity, and desugaring questions. This
started as a sketch. It is now built, in Clang, behind a flag, and the parts
of the sketch the build contradicted are the interesting half of the post.
#+end_abstract

{{{TEASER_END}}}

* The pitch, again in one line

The backtick proposal says =x `f` y= is =f(x, y)= for any callable =f=. Once
you have that, people ask the next question: fine, any /name/ can be an
operator, but what about actual /symbols/? Mathematics didn't stop at the
dozen operators ASCII happens to contain, and neither did Unicode. So the
sketch is this: let a user declare

#+begin_src c++
constexpr int operator⊞(int a, int b) { return a + b; }
constexpr Matrix operator⊗(Matrix const&, Matrix const&);
#+end_src

and then

#+begin_src c++
5 ⊞ 7                   // operator⊞(5, 7)
a ⊗ b ⊗ c               // operator⊗(operator⊗(a, b), c)
#+end_src

=operator⊞= is an ordinary function: overloadable, member or free, found by
ADL, usable in templates, callable by its full name if you want to. The
expression form desugars to the call in the front end, the same way
backtick does, so overload resolution, templates, constexpr, and codegen are
all inherited instead of reimplemented. That part of the design is settled;
the backtick work already litigated it.

These characters can never collide with the language. C++ has never assigned
=⊞= a meaning; today it isn't even a valid token, and a source file
containing one fails to lex. The space is empty, and it's large.

All of that was true when I wrote the sketch. What's new is that I built it.
Clang, on a branch off trunk, behind =-funicode-operators=, default off: the
token set, the operator name, mangling, infix and prefix uses, the AST node,
modules, an AST matcher, clang-format. Two thousand lines of compiler. Where
the rest of this post says something confident, it's because a compiler said
it, and where it says I was wrong, that's a compiler too.

* Unicode already did the standards work

I spent part of the backtick effort cataloguing what's left of ASCII. The
answer is: almost nothing, and everything that remains is two characters
glued together with adjacency hazards. That inventory is why backtick
exists: named operators cost no lexical real estate at all.

The non-ASCII space is different in kind, and as of last year it has a
standard behind it. UAX #31 (the Unicode identifier-and-syntax annex, the
same document C++23 already cites for identifiers, via P1949) now has a
section on user-defined operators: UAX31-R3c. It defines operator characters
in terms of the =Pattern_Syntax= property, and =Pattern_Syntax= carries the
strongest promise Unicode makes about anything: it is immutable, per code
point. No code point will ever gain or lose the property, in any version,
ever. That's the stability policy, in force since Unicode 4.1 in 2005.

But immutable isn't closed, and the distinction is the first question any
committee will ask. The frozen set is 2,760 code points, and 79 of them are
still unassigned; Unicode has been filling them in steadily, 453 new
characters since the freeze, including one in 17.0 itself (⮖, EQUALS SIGN
WITH INFINITY ABOVE, which certainly sounds like something someone will want
as an operator). So Unicode 18.0 can mint new symbols /inside/ the set; what
it can not do is mint one outside it. The consequence for C++ is that the
operator set has to be a frozen enumeration, pinned to a Unicode version,
never re-derived: a new character can't be checked against the confusables
list before it exists, so nothing gets in automatically. A later revision of
the standard could adopt new symbols the way it adopts anything else, by
paper, on purpose. The ceiling is guaranteed; the contents are a decision.

One correction to my own first reading, for anyone else skimming TR31: §7.1,
the "Mathematical Compatibility Notation Profile," sounds like the operator
section and isn't. It's an /identifier/ profile: it's about letting =∂=,
=∇=, and =∞= be identifier characters, and it removes them from syntactic
use. The operator story is R3c. And it means those three characters belong to
the identifier side of the line, so they're excluded from any operator set:
they name things; they don't combine things.

R3c's raw set won't do as-is, since =Pattern_Syntax= includes all the ASCII
punctuation C++ already spent. The usable pool is Pattern_Syntax minus ASCII,
restricted further: single code points from the mathematical and arrow
blocks, general category Sm or So, excluding the paired brackets (=⟨=, =⟦=,
=⌈=; worth keeping unspent for some future bracketing idea) and excluding
anything confusable with an existing token. That last list matters most:
U+2212 (the real minus sign), the division and fraction slashes, the asterisk
operator, the two dot operators, =≤= and =≥=. Those are rejected outright,
never aliased. A character that renders like =-= but isn't should fail to
compile, not quietly mean something else. What's left, with every exclusion
applied, is 1,381 code points in 32 contiguous ranges: =⊞ ⊠ ⊕ ⊖ ⊗ ⊘ ∘ ⋄ ⋈ ∪ ∩
⊓ ⊔ ↦ ⊢ ⊨= and on and on. (Those 32 ranges are also the entire lexer story: a
256-byte sorted table, one binary search, on the slow path that only non-ASCII
source reaches. Both compilers already classify extended identifiers with
exactly this machinery.) Actual notation, where ASCII offered scraps.

The exclusion list came out at 28 code points: three identifier characters,
thirteen confusables, and twelve with emoji presentation. Two things about it
I'd have got wrong on paper. Enumerating it forced me to notice that "the
middle-dot family" is not a thing the UCD has: inside these blocks it's
just U+2219 and U+22C5, because U+00B7 MIDDLE DOT isn't =Pattern_Syntax= at
all, since Unicode withheld it precisely because Catalan uses it /in/
identifiers. And the ASCII token named beside each confusable is curated,
not derived, deliberately, because the published confusability tables answer
"what does this look like" while a diagnostic needs "which C++ token does this
look like", and those come apart. U+2219 and U+22C5 both /mean/
multiplication and both /look like/ =.=, and it's the look that endangers a
reader. =⇔= is spelled =<=>=, a token this language acquired in 2020, which no
general-purpose confusability table is obliged to know about.

That also settles the wording. The message says the character /is confusable
with/ the token, never "did you mean", and carries no fix-it. Nobody writing
=a ∙ b= meant =a . b=. A confusability claim is an assertion about reading and
an intent guess is an assertion about writing, and only the first is one a
compiler has any business making.

* Parsing is the easy part this time

Backtick had one genuinely tricky parsing problem: the open and close
delimiter are the same token, which needed a =GreaterThanIsOperator=-style
suppression flag in both compilers. None of that applies here. Each operator
is one distinct token. There's no delimiter to match, no nesting question, no
suppression flag. The grammar work is close to nothing:

- Binary =⊞= sits at the same precedence level as backtick (the highest
  binary level, tighter than =*=, looser than unary) and it's
  left-associative. One level for all user-introduced infix, named or
  symbolic, so mixed chains group left and there is no precedence table to
  memorize. =-a ⊞ -b= is =operator⊞(-a, -b)=, symmetric, for the same
  reasons the backtick design records.
- Unary prefix operators are declared with one parameter, the way
  =operator-= already selects its form by arity. Position disambiguates a
  use: after an operand it's binary, in operand position it's prefix. That's
  the rule C++ has always used for =-=, =*=, and =&=. No postfix forms; that
  is what forces Swift into whitespace-sensitivity rules, and declining
  postfix avoids the whole topic.

One structural point that constrains everything: whether =⊞= is an operator
token can not depend on whether an =operator⊞= declaration is in scope.
Lexing happens long before name lookup (the preprocessor sees the tokens
too). So the character set is fixed by the grammar, and using an operator
nobody declared is an ordinary overload-resolution failure, the same
diagnostic as =std::cout << my_type{}= without a =<<= overload. This is
Julia's model (the parser has a fixed table of operator characters; users
just define methods for them), and it's the only model that can work in
C++.

All of that held. The infix production is one =case= in the precedence table
and a fourteen-line arm in the binary-expression loop. The prefix production
is one =case= in the cast-expression parse, about forty lines. And the reason
position alone can decide prefix versus infix, with no lookahead and no
whitespace rule, turns out to be sharper than "the grammar alternates": the
two productions are read by two /different functions/, one only ever in
operand position and one only ever after a complete operand, so they never
examine the same token. There is no disambiguation state to get wrong,
because there is none at all. Compare backtick, where the open and close
delimiter are the same token and a suppression flag has to be threaded
through the slot in both compilers.

* The hard parts are elsewhere, and I under-priced them

I wrote that parsing is the easy part of this feature, easier even than
backtick. The first half is right and the second half isn't, and I think the
way it went wrong is worth more than the correction.

The parse really is small, on both sides. But the parse isn't where the cost
lives. Backtick's cost is in the parse and stops there. This feature's cost is
in what a parsed operator has to /become/: a name, in tables that are closed,
and an expression node that can't be transparent. So the comparison inverts
the moment you leave the parser, and the sketch claimed credit it didn't have.

Why it went wrong is the general lesson. It wasn't a bad guess about the
parser; the parser estimate was right and stayed right. It was a design
document measuring the part of a feature a design document can see. The parse
is visible from the grammar, so it gets estimated. The name tables and the
node are invisible until something is built, so they get left out, and leaving
them out reads like a claim that they're small. I'd expect that error
in any implementation sketch, and in that direction.

The declaration side was the part I did see coming. Clang represents
=operator+= as a =DeclarationName= over a closed enum of operator kinds, and
GCC keeps operator identifiers in a fixed-size table; =operator⊞= fits
neither. Both compilers already solved this shape once, for user-defined
literals: =operator""_km= is an operator name carrying open-ended extra data,
threaded through declaration, lookup, and mangling. That transplanted almost
line for line, 250 lines over 19 files, which is a number I'd cite as an
argument /for/ the design.

The sharp edge was somewhere else, and it's a good story about closed tables.
The new name kind isn't a choice. Clang's inline three-bit space for name
kinds is completely full, so any new kind is forced out into the overflow
struct, and the overflow struct's tag can't be appended to either, because it
encodes an N-argument Objective-C selector as =base + N= and clamps everything
at or above that back down. The new kind has to be /inserted before/
Objective-C's, renumbering an enum in a shared header. The operator-name space
isn't merely closed. It's packed against another language's variable-length
encoding. That tells you how much of the difficulty is inherent to open-ended
operator names (very little) and how much is one compiler's bit-packing
(nearly all of it).

Mangling is the one place the feature touches ABI, and it's smaller than I
feared. The Itanium ABI has a vendor-extended operator production for this
very situation, so the prototype mangles =⊞= as a derived ASCII name today,
=op_u229E=, and both =llvm-cxxfilt= and GNU binutils =c++filt= (a different
vendor's demangler, unmodified) render every form I tested: free function,
const member, explicit-object member, template instantiation. Nothing in the
toolchain needs a change to inspect these symbols, which is the first thing an
ABI reviewer asks about.

The paper still asks for a first-class production, for one reason worth
stating: the vendor production keys on /arity/, and arity isn't fixity. Prefix
and postfix unary operators both have arity one. I'm not proposing postfix, but
I am careful not to foreclose it, and adopting an arity-keyed encoding as the
standard answer would foreclose it quietly. The ABI already spends four codes
keeping unary =+ - & *= apart from their binary selves, so distinguishing
forms of one symbol is a principle it holds already. The vendor production is
just the one place it has no room to.

Windows is the honest gap. The Microsoft ABI has no such production, and the
prototype declined to invent one: a Windows target accepts every declaration,
because the name is representable, and rejects the first definition with a
"can't mangle this yet" diagnostic. Inventing a scheme would have been binding
on Windows the day it shipped.

And there's the objection everyone raises first: how do you type =⊞=? The
honest answer is Julia's answer — editor input methods. =\boxplus= and hit
tab, in every editor Julia's community touched, and that community has run
this experiment at scale for over a decade. Code is read far more often than
it's typed. The fallback is always there: =operator⊞(a, b)= is an ordinary
call, and a codebase that hates the glyphs can simply not declare any. I'd
also note, having fought shell quoting for a year, that =git grep ⊞= just
works, which is more than I can say for the backtick.

* What I am not proposing: precedence declarations

Every language that lets users pick fixity regrets it somewhere. Haskell's
=infixl 6= travels with imports, so the parse of an expression depends on
what's in scope. Swift's precedencegroups reintroduce the same thing with
more ceremony. In C++ the failure mode has a name: two translation units
that disagree about how =a ⊕ b ⊗ c= parses are an ODR violation factory,
and modules make the question of "which fixity declarations are visible
here" genuinely unanswerable.

So: one precedence level, fixed by the language, left-associative,
parenthesize for anything else. The parse of every expression depends on
nothing but the expression. Only the /meaning/ of =operator⊞= travels, and
that's ordinary name lookup, which C++ already knows how to do across TUs.
OCaml is the existence proof that programmers accept fixed, non-declarable
fixity for user operators (there, derived from the operator's first
character) and mathematicians who want =⊗= tighter than =⊕= can write the
parentheses. Left to right is the least surprising reading; everything else
is what parentheses are for.

* Two things the build told me that no amount of writing would have

The first is a bug that never shipped, because it was caught, but which shows
what "structurally free" can hide. I'd written that admitting the escaped
spelling =operator\u229E= alongside the glyph =operator⊞= was structurally
free: the lexer already decodes universal-character-names, and the resulting
code point takes the same classification either way. Classification /is/ free. Identity isn't. The first
cut derived the operator's identity by decoding the token's spelling as one
UTF-8 scalar, which answers zero for a UCN. That value is the =DeclarationName=,
the mangled symbol, the printed form, and the on-disk lookup key. So
=operator\U0000229E= would have been a /different entity/ from =operator⊞=,
with a different symbol, while the token kind, the token stream, and
=-dump-tokens= all looked perfectly correct.

The thing I want to keep from that: no token-level test can see it. The only
test that catches it declares with one spelling, defines with another, uses
with a third, and asserts one entity and one mangled symbol. "Equivalent
spellings" is a claim about /entities/, and a test written at the level of
the claim you meant to make is a different test from the one written at the
level of the mechanism.

The second is a present rather than a bug. The desugaring says =x ⊞ y= is the
call =operator⊞(x, y)=, so it ought to get the call's lookup. It does, and I
wrote no code for it. Because the callee is a name the compiler forms from the
token and never an expression the parser resolves, the unresolved set reaches
overload resolution with the arguments in hand, and ADL just happens: hidden
friends, ADL-only namespace members, augmentation of a visible-but-worse
candidate, ADL at instantiation. About a dozen lines.

That's worth reporting because the backtick project got the same thing wrong
in both of its compilers, in the same way: each resolved the slot's name in
the parser, and each silently lost ADL. Same author, same week, same idea.
Desugar early and everything downstream is inherited; /resolve/ early and
it isn't.

* What the node costs

The desugaring is exact for a non-dependent use, and that's not the whole
story. When an operand is type-dependent the expression is rebuilt at
instantiation, and an ordinary call rebuilds under the rules for a call.
ADL survives, because ADL is a property of the call. Member candidates don't,
because being written as an operator is a property of the /syntax/. So a
template over =a ⊕ b= failed for a member =operator⊕=, and the obvious concept
was unsatisfied for a type whose only =⊕= is a member. The desugaring was
exact and the compiler still gave the wrong answer, which is a shape of
finding a design document can't produce.

The fix is a node that records the operator-ness and re-runs the resolution at
instantiation rather than replaying the result, on the model of the rewritten
comparison operators C++20 already has. It's a strict cost of the feature and
it's the one place this is /more/ work than backtick, because a backtick slot
has no member candidates to lose.

What that node then obliges is the part I'd put in front of anyone estimating
a language feature. Adding a name kind, a declarator-id kind, and an expression
node came to 89 dispatch sites on three axes that share no site. For the
node's 43, the interesting question isn't how many. It's which ones the
toolchain made me find: six by a link error, eight by an =llvm_unreachable=,
two by a warning on a build with warnings-as-errors off, three that are simply
/absent/ rather than wrong, four that were latent behind a CMake default
nobody had turned on, one that exists only because two other obligations were
met correctly, and nineteen that nothing at all announces. The toolchain finds
about a third and is quiet about the rest.

Two of those sites are =||= chains instead of =switch= arms, and five more on
another axis are chains of equality tests against the same enum. A =switch=
over a closed enum is checked and a chain of comparisons isn't, and the two
are interchangeable at the moment somebody writes them. Whether the compiler
helps you is a property of how a site was /spelled/, not of what it dispatches
on. Estimating this
feature from the shape of the enums under-counts by exactly the sites somebody
once wrote as an =if=.

* Where this leaves backtick

The two features are complementary, and deliberately so. Backtick lifts any
name into infix position with zero declarations; this lifts symbols, at the
price of one. And backtick is the honest baseline the symbolic version has to
beat: most of the value is available today by naming the function well;
=a `boxplus` b= works fine. The residual case for symbols is the domains
where the notation /is/ the vocabulary (linear algebra, lattices,
relational algebra, units), where =`tensor`= is a transliteration of the
thing and not the thing.

APL is the ghost at this feast, so name it: the objection is glyph soup that
nobody can read or type. But APL's glyphs were primitives, with no
declaration to go read. These are user-named functions; =operator⊗= has a
declaration, in a header, with a comment, found by go-to-definition. The
notation is only as opaque as the library that declares it, which is exactly
as true of =operator<<= today.

This is a separate paper from the backtick one, citing its decisions without
reopening them, and sequenced so that a committee allergic to Unicode can't
take the backtick down with it. SG16 gets it before EWG does.

That separability isn't a promise any more. The work was prototyped on top of
the backtick branch and then replayed onto pristine trunk, and 201 of 204
hunks came across unchanged (169 of 171 in the compiler proper). The replayed
branch mentions backtick nowhere: not in the code, in a test, or in a commit
message. The whole coupling between the two features is three constructs, and
only one of them is a design decision: the shared precedence level. The other
two are the fold-operator exclusion of that level, and one predicate in
clang-format that has to agree about where an operand ends.

The shared level surfaced twice, independently: once in the parser as a
precedence value, once in the formatter as an end-of-operand predicate, in two
subsystems that don't know about each other, each of which had to ask "is this
a user-introduced infix operator?". That's a real design primitive rather than
a convenience of my prototype, and whichever of the two papers goes first
should bank it for both.

* What isn't done yet

One compiler. Backtick's strongest asset is two independent implementations
that agree, and this has Clang only, which is the asymmetry that keeps
the two papers apart: a single-implementation half shouldn't get to spend the
two-implementation half's credibility. GCC's move is the same one — its
operator identifiers live in a fixed-size table indexed by tree code, and
=cp_literal_operator_id= already synthesizes an identifier outside that table
for =operator""_suffix= — but nobody has written it.

Windows mangling is open and needs the vendor. The evaluation-order question
is open and needs CWG: for a member operator the left operand is the object
expression, so it's sequenced before the right one, and for a non-member it
isn't, which makes the sequencing of =x ⊞ y= depend on overload resolution. No
existing C++ operator behaves that way, because every overloadable operator
today borrows its sequencing from a built-in and this one has no built-in to
borrow from. I don't propose an answer; I think the room should pick one.

Combining marks (=⊕̸= and friends) and the Latin-1 stragglers (=±=, =×=, =÷=,
=¬=) are deliberately outside the frozen set and are coherent extensions for a
later revision. Postfix is declined and carefully not foreclosed: I built the
one lookahead rule that works, measured what it costs, and threw it away. It
turns every missing right operand into a valid postfix parse, which is a
diagnostic every user of the feature pays for whether or not anyone declares a
postfix operator.
