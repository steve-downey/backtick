# Deviation ledger — Unicode operators, Clang track

Each row is a place the build taught us something `docs/unicode-operators.md`
didn't know. Unlike the backtick ledgers, this one runs against a design
that is entirely **Proposed** — a row here is not an embarrassment, it is
the point of building the prototype. The paper author reconciles rows into
U§2 (decisions log) and the affected U§ section.

Record cross-compiler divergences (Clang vs GCC vs the backtick tracks)
here too; they are exactly what SG16/EWG/CWG ask about.

| DEV-U04 | U06 | U§8 "Clang — *The hard part — `DeclarationName`*" | "Overloaded operators are `CXXOperatorName` over the closed `OverloadedOperatorKind` enum… User operators need a new `DeclarationName` kind carrying the code point. What the sketch does not say: (a) the new kind is not a *choice* — the inline 3-bit `StoredNameKind` space is **completely full** (all eight values 0–7 taken), so any new kind is *forced* through `DeclarationNameExtra`; the literal-operator route is the only route. (b) `DeclarationNameExtra::ExtraKind` **cannot be appended to**: the single field `ExtraKindOrNumArgs` encodes an N-argument Objective-C selector as `ObjCMultiArgSelector + N`, and `getKind()` clamps every value ≥ `ObjCMultiArgSelector` back to it, so appending `CXXUserOperatorName` after it would silently misclassify every multi-keyword selector. It must be *inserted before* `ObjCMultiArgSelector`, renumbering `ExtraKind` 3→4 and `NameKind::ObjCMultiArgSelector` 11→12. (c) One of the 33 sites is **generated**, from `clang/include/clang/AST/PropertiesBase.td` into `AbstractBasicReader/Writer.inc` — it is not greppable as C++ and only the `-Wswitch` warning finds it. | U§8's `DeclarationName` paragraph should quantify rather than hedge: "a real cost" becomes "~250 lines across 19 files and 33 switch sites, one of them TableGen-generated" — a number the paper can defend, and small enough to be an argument *for* the design rather than a caveat. Then replace the "worked precedent" reassurance with the real finding: the operator-name space is not merely closed, it is **packed against Objective-C's variable-length selector encoding**, so opening it costs an enum renumbering in a shared header rather than a new enumerator. That is the sentence a committee reader wants — it says exactly how much of the difficulty is inherent to open-ended operator names (little) and how much is an accident of one compiler's bit-packing (most of it), and it is the kind of evidence GCC's `ansi_opname` half of U§8 should be measured against in the same units. |

| DEV-U06 | U08 | U§7 "Declaring"; U2, U5 | "*operator-function-id* grows one production… Everything downstream is the existing machinery: free function or member, any parameter types, templates, `constexpr`, `= delete`, the lot. Measured against `Sema::CheckOverloadedOperatorDeclaration`: (a) **class-or-enum parameter** — waived, as U2 says; (b) **no default arguments** ([over.oper]p8, `err_operator_overload_default_arg`) — must also be waived, and the design never says so; (c) **not variadic** (`err_operator_overload_variadic`) — likewise waived; (d) **the arity table** (`OperatorUses[Op]` from `OperatorKinds.def`) — has no entry to consult, so the prefix/infix rule has to be written out; (e) **not a static member** (`err_operator_overload_static`) — *kept*, and this one is a judgement U08 had to make with no guidance from the design: U5's arity rule is stated as "two parameters, or one as a member", which presupposes an implicit object parameter, and a static member function has none, so it can name neither form. | DEV-U08 | U09 | U§9 (ABI and mangling); U8 | "the Itanium **vendor-extended operator** production, `v <digit> <source-name>` … e.g. binary `⊞` mangles as `v2` plus a code-point-derived source-name such as `op_u229E`, giving stable, demangler-tolerated symbols for the fork", with the two productions "disjoint by the mangling grammar itself". | **The production works, and three things the design leaves implicit had to be decided or measured.** (a) **`op_u229E` is an example, not a rule.** U09 had to write the rule down, and it is now stated verbatim in `ItaniumMangle.cpp`: `"op_u"` + the code point in **uppercase** hex, no `U+` prefix, zero-padded to a **minimum of four** digits and widened above the BMP (five from U+10000, six from U+100000), emitted as an ordinary `<source-name>` (decimal byte length, then the identifier) exactly as `li <source-name>` does. Injectivity comes from hex, not from the padding — leading zeros only ever reach four digits and every code point above 0xFFFF is already five — so no two operators can collide. Note the padding and the widening are both **unexercised by construction today**: every U1 code point is in 0x2190–0x2BFF, so every derived name is exactly four digits. (b) **"Demangler-tolerated" understates the result.** Measured: `llvm-cxxfilt` *and* **GNU binutils `c++filt` 2.46** — a different vendor's demangler, unmodified — both render the `v` production readably in every form tested, including nested-name, const-qualified member, C++23 explicit-object member and template-id: `_Zv28op_u229E1SS_` → `operator op_u229E(S, S)`, `_ZNK1Tv28op_u229EES_` → `T::operator op_u229E(T) const`, `_Zv28op_u22A0IiEiT_S0_` → `int operator op_u22A0<int>(int, int)`, `_ZNH1Ev28op_u2297ES_S_` → `E::operator op_u2297(this E, E)`. Existing toolchains need **no change** to inspect these symbols. (c) **The arity digit is stable where linking uses it and follows the expression elsewhere — and that is upstream's shape, not this feature's.** In `<base-unresolved-name>` position (a dependent `decltype(t.operator⊞(t))`) the digit is the *call's* argument count, so a member infix operator whose definition mangles `v2` mangles `on v1 …` there. Upstream does exactly the same for the built-in operators — `decltype(t.operator+(t))` mangles `onps`, i.e. **unary** plus, for a binary member `operator+` — so it is inherited behavior, invisible to linkage (the defining symbol is unaffected), and bug-compatible with what a demangler already expects. | Give U§9 the derivation **rule** rather than the example, in the wording above; it is the sentence the paper will be quoted on and the sentence an ABI group would review. Upgrade "demangler-tolerated" to the measurement — *two* independent demanglers, one of them binutils, render every form with no changes — because that is the strongest thing the prototype can say about the `v` production and it is exactly the question an ABI reviewer asks first. Then add the arity nuance as a footnote, and note what it argues: a first-class `<operator-name>` keyed by code point (the thing U8 flags as the real answer) has **no arity digit to disagree about**, so the wrinkle is one more small reason to prefer it over the vendor-extended form once the feature standardizes. |

| DEV-U10 | U10 | U§7.1's fourth point ("the payoff of a both-classes character would be nil"); U§7 "Using"; U2 | U§7.1 argues that a bare-identifier `⊞` buys nothing because **"`operator⊞` *is* the name of the function: `operator⊞(a, b)` calls it, `&operator⊞` takes its address, and the operator-function-id names the overload set anywhere an unqualified-id does — exactly as `operator+` works for existing operators."** U§7 "Using" separately makes ADL normative (U6, §17.4). | **Both claims hold, and the ADL one holds unusually strongly — measured, not assumed.** Every position in U10's sweep works with *zero* production changes: constant evaluation, overload ranking, qualified/member/arrow/class-qualified calls, address-taking (`&`-ed, bare, as a non-type template argument, target-typed out of an overload set, as a pointer to member), templates, SFINAE, `requires`, dependent calls. ADL specifically: hidden friends reachable by nothing else, enumerations, pointer operands, class-template arguments, and **augmentation of a non-viable ordinary-lookup set** all work, and ADL correctly declines to find member operators and is correctly suppressed when ordinary lookup finds a class member. **The exception is one word: "anywhere".** A *dependent* object expression with the `template` disambiguator — `t.template operator⊞<int>(0)` — is rejected with `'operator⊞' following the 'template' keyword cannot refer to a dependent template`.
