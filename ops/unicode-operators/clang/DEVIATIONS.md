# Deviation ledger — Unicode operators, Clang track

Each row is a place the build taught us something `docs/unicode-operators.md`
didn't know. Unlike the backtick ledgers, this one runs against a design
that is entirely **Proposed** — a row here is not an embarrassment, it is
the point of building the prototype. The paper author reconciles rows into
U§2 (decisions log) and the affected U§ section.

Record cross-compiler divergences (Clang vs GCC vs the backtick tracks)
here too; they are exactly what SG16/EWG/CWG ask about.

(b) **U+2044 ⁄ FRACTION SLASH is not in the U1 blocks** (it is U+2044, the blocks start at U+2190), so it already fails predicate 3; listing it under predicate 5 is harmless but misleading — of the 16 named exclusions it is the only one that would not otherwise have qualified. (c) U§8 wants the exclusions to carry the token they ape, but the list assigns none per character; U02 assigned them: − → `-`, ∕ ⁄ → `/`, ∗ → `*`, ∣ → `|`, ∶ → `:`, ∙ ⋅ → `.` (they are dot-shaped; the *visual* confusion is with `.`, not with the `*` their mathematics means), ≤ ⇐ → `<=`, ≥ → `>=`, ⇒ → `=>`, ⇔ → `<=>` (C++20 has a token that shape). The emoji-presentation exclusion resolves to **12** code points inside the blocks (⌚ ⌛ ⏩ ⏪ ⏫ ⏬ ⏰ ⏳ ⬛ ⬜ ⭐ ⭕). | Replace U§5 predicate 5's prose with the enumerated 16 + a pointer to the 12 emoji code points, each with its reason and (for a confusable) the token it apes — i.e. print the generated `ExcludedOperatorChars` table in the paper. | DEV-U04 | U06 | U§8 "Clang — *The hard part — `DeclarationName`*" | "Overloaded operators are `CXXOperatorName` over the closed `OverloadedOperatorKind` enum… User operators need a new `DeclarationName` kind carrying the code point. The precedent is **`CXXLiteralOperatorName`**… This is a real cost — DeclarationName plumbing fans out — but it is a *worked* precedent, not terra incognita." | **The precedent held exactly, and the cost is smaller than the sentence implies — but the sharp edge is somewhere else entirely.** Measured: **33** switch sites over `DeclarationName::NameKind` across 20 files; the whole step is **21 files, +436/−1 lines**, of which **19 files / +249 lines** are production code and 186 lines are the new unittest. `CXXLiteralOperatorIdName`'s shape transplants almost line for line. What the sketch does not say: (a) the new kind is not a *choice* — the inline 3-bit `StoredNameKind` space is **completely full** (all eight values 0–7 taken), so any new kind is *forced* through `DeclarationNameExtra`; the literal-operator route is the only route. (b) `DeclarationNameExtra::ExtraKind` **cannot be appended to**: the single field `ExtraKindOrNumArgs` encodes an N-argument Objective-C selector as `ObjCMultiArgSelector + N`, and `getKind()` clamps every value ≥ `ObjCMultiArgSelector` back to it, so appending `CXXUserOperatorName` after it would silently misclassify every multi-keyword selector. It must be *inserted before* `ObjCMultiArgSelector`, renumbering `ExtraKind` 3→4 and `NameKind::ObjCMultiArgSelector` 11→12. (c) One of the 33 sites is **generated**, from `clang/include/clang/AST/PropertiesBase.td` into `AbstractBasicReader/Writer.inc` — it is not greppable as C++ and only the `-Wswitch` warning finds it. | U§8's `DeclarationName` paragraph should quantify rather than hedge: "a real cost" becomes "~250 lines across 19 files and 33 switch sites, one of them TableGen-generated" — a number the paper can defend, and small enough to be an argument *for* the design rather than a caveat. Then replace the "worked precedent" reassurance with the real finding: the operator-name space is not merely closed, it is **packed against Objective-C's variable-length selector encoding**, so opening it costs an enum renumbering in a shared header rather than a new enumerator. That is the sentence a committee reader wants — it says exactly how much of the difficulty is inherent to open-ended operator names (little) and how much is an accident of one compiler's bit-packing (most of it), and it is the kind of evidence GCC's `ansi_opname` half of U§8 should be measured against in the same units. |
| DEV-U05 | U07 | U§8 "Clang" bullet list; U§6's "parsing is the *easy* part of this feature, easier even than backtick"; U§7 "Declaring" | U§8's three Clang bullets are *Lexer*, *Parser* ("the `prec::Level` introduced for backtick serves as-is; a `tok::user_operator` case joins `tok::backtick` in `ParseRHSOfBinaryExpression`, and a case in `ParseCastExpression` handles the prefix form") and *the hard part — `DeclarationName`*. U§7 gives the declaring side one sentence: "*operator-function-id* grows one production… Everything downstream is the existing machinery." | **The headline claim holds — and the omitted half is now measured.** U§8's Parser bullet describes only *expression* parsing (U11/U12); the *declaring* side, which is where `operator⊞` becomes a name at all, is a separate and slightly larger piece of parser work: **8 production files, +89/−5 lines**, namely a new `UnqualifiedIdKind` with its payload and setter, one arm in `ParseUnqualifiedIdOperator`, one arm in `Sema::GetNameFromUnqualifiedId`, and **9 peer sites** that had to learn the kind — four template-id paths in `ParseExprCXX.cpp`, `Sema::isTemplateName`, and four `UnqualifiedIdKind` switches in `SemaDecl.cpp`/`SemaType.cpp`/`SemaDeclCXX.cpp` (all exhaustive, so `-Wswitch` found them; the build is warning-clean). Two findings inside that: (a) **tentative parsing needed a peer change the design does not anticipate.** `Parser::TryParseOperatorId` handles `operator new/delete`, the `OperatorKinds.def` punctuators, `()`, `[]`, a literal-operator-id, and *otherwise assumes a conversion-type-id follows*; a `tok::user_operator` fell through to that loop, found no decl-specifier, and returned `TPResult::Error`, so an ambiguous statement such as `S operator⊛(S, S);` was re-parsed as an expression and rejected. One four-line case fixes it. The backtick track needed a peer change in the *same file* at its S08, for an unrelated reason — so "tentative parsing has to be told about any new declarator-id token" is a two-for-two result across the two features, not a coincidence. (b) `TemplateIdAnnotation` has no slot for a code point, exactly as it has none for a literal-operator suffix (the pre-existing `// FIXME: Store name for literal operator too.`), so `operator⊞<T>` parses and resolves through the `TemplateName` while the annotation carries `nullptr`/`OO_None`. Upstream's one-line `OpKind` expression also *reads the wrong union member* for a literal-operator-id; U07 had to make that read kind-checked rather than inherit the bug for a `uint32_t` payload. | Split U§8's Parser bullet in two — *declaring* and *using* — and give the declaring half the measurement (~90 lines, 8 files, one new `UnqualifiedId` kind, 9 peer sites, all compiler-found) next to U§7's "grows one production". It supports U§6's claim rather than undercutting it: the parse cost really is small, and it is *smaller than the `DeclarationName` cost* (DEV-U04's ~250 lines / 33 sites), which is the ordering the design predicts. Then add the tentative-parsing sentence as a portable implementation note — "a compiler that disambiguates declarations from expressions by trial parse must teach that path the new token too; both Clang prototypes needed it" — because it is the one place the declaring side is *not* just "the existing machinery", and GCC's `cp_parser_*` tentative machinery will face the same question. |
| DEV-U06 | U08 | U§7 "Declaring"; U2, U5 | "*operator-function-id* grows one production… Everything downstream is the existing machinery: free function or member, any parameter types, templates, `constexpr`, `= delete`, the lot. Arity selects the form (U5)… Unlike the existing operators there is **no class-or-enum parameter requirement** (U2)." The only named departure from [over.oper] is the class-or-enum rule. | **"The existing machinery" is the wrong frame for the declaring rules, and the class-or-enum rule is not the only [over.oper] rule that must not carry over.** [over.oper] imposes five restrictions on an operator function, and a user operator inherits exactly *one* of them. Measured against `Sema::CheckOverloadedOperatorDeclaration`: (a) **class-or-enum parameter** — waived, as U2 says; (b) **no default arguments** ([over.oper]p8, `err_operator_overload_default_arg`) — must also be waived, and the design never says so; (c) **not variadic** (`err_operator_overload_variadic`) — likewise waived; (d) **the arity table** (`OperatorUses[Op]` from `OperatorKinds.def`) — has no entry to consult, so the prefix/infix rule has to be written out; (e) **not a static member** (`err_operator_overload_static`) — *kept*, and this one is a judgement U08 had to make with no guidance from the design: U5's arity rule is stated as "two parameters, or one as a member", which presupposes an implicit object parameter, and a static member function has none, so it can name neither form. U08 rejects it, reusing the existing diagnostic. Structurally, the consequence is that `CheckUserOperatorDeclaration` is a **sibling** of `CheckOverloadedOperatorDeclaration`, not a widening of it — 54 lines that share no code with it — and that is also what makes "no existing operator's rules moved" provable rather than merely tested (the shared checker was never touched; the class-or-enum branch is unreachable from the new path rather than conditionally skipped). | Rewrite U§7 "Declaring" to enumerate the five [over.oper] restrictions and say which survive, rather than naming only the class-or-enum one. The generalization is sharper than the current sentence and worth stating as such: **[over.oper]'s restrictions exist to protect a token whose parse, arity and fixity the grammar already fixed; a user operator's only fixed property is arity, so arity is the only rule it inherits.** Default arguments and variadic parameter lists then fall out as *allowed* by derivation rather than by fiat. Add the static-member decision to the decisions log as a sub-point of U5 (or a new U-number) with its rationale — it is a small, real, litigable choice, and the C++23 `static operator()` precedent means someone will ask whether a static member user operator should be admitted as a second infix form. Also worth one sentence for the paper's implementation section: the checker is a sibling, not an extension, and that is why the relaxation provably cannot leak into `operator+`. |
| DEV-U07 | U08 (question raised by U01) | U7; U§8's flag story | `-funicode-operators` is "gated behind its own flag… independent of and composable with `-fbacktick`", with a "default build byte-identical to upstream". Nothing says what the flag means outside C++. | **The flag is accepted in C mode and, since U03, is no longer inert there.** Measured on `int f(int a, int b) { return a ⊞ b; }` compiled as C: with `-funicode-operators`, one error (`expected ';' after return statement`); without it, two (`unexpected character '⊞' U+229E`, then the same recovery error). So the flag *does* change C-mode behavior — it suppresses the accurate diagnostic and leaves only the misleading one. It cannot ever do anything useful there: C has no `operator` keyword, so no `operator⊞` can be declared and the token has no production to appear in. `-fbacktick` has the identical property. The precedent for fixing it is one line: `defm reflection` in `Options.td` carries `ShouldParseIf<cplusplus.KeyPath>`; neither `defm backtick` nor `defm unicode_operators` does. | **Recommendation: both flags should gain `ShouldParseIf<cplusplus.KeyPath>`, and should gain it together.** U08 did not make the change — it is outside a Sema-declaration-rules step, it edits U01's driver test, and a divergence where one of the two paired flags is C++-only would be a worse surprise than the current symmetry. Record it as a small follow-up (a U04/U05-adjacent lexer step is the natural owner, since the observable is a *lexing* difference). For the paper this is a one-line footnote at most, but it is the kind of thing an implementer replaying the patch will hit: **a feature whose grammar is C++-only should not have a flag that changes C tokenization.** |
