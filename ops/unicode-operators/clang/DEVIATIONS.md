# Deviation ledger — Unicode operators, Clang track

Each row is a place the build taught us something `docs/unicode-operators.md`
didn't know. Unlike the backtick ledgers, this one runs against a design
that is entirely **Proposed** — a row here is not an embarrassment, it is
the point of building the prototype. The paper author reconciles rows into
U§2 (decisions log) and the affected U§ section.

Record cross-compiler divergences (Clang vs GCC vs the backtick tracks)
here too; they are exactly what SG16/EWG/CWG ask about.

(The `ID_Compat_Math_Start` table does contain exactly ∂ U+2202, ∇ U+2207, ∞ U+221E plus 10 Mathematical-Italic variants, as U10 asserts.) | Note in U§4 that the frozen U1 set is pinned to UCD 17.0 **by the proposal** while implementations track whatever UCD their identifier tables use — that separation is the point of U1, but the disjointness claim in U§7.1/U10 should be re-stated as verified at 17.0 *and* 18.0 once U02 measures it. If U02's cross-check finds any overlap at 18.0, that is a U10 finding, not a table bug. **Measured by U02 (2026-08-03): no overlap — see DEV-U02.** |
| DEV-U02 | U02 | U§7.1, U10 (resolves the DEV-U01 open question) | Disjointness of the operator set and identifier space is asserted against UCD 17.0 only ("Pattern_Syntax ∩ XID_Start = Pattern_Syntax ∩ XID_Continue = ∅ in UCD 17.0"). | Measured in-tree, per code point, over all 1,381 U1 members against Clang's own tables — which are labelled **Unicode 18.0**: **zero** are XID_Start, zero XID_Continue, zero in `MathematicalNotationProfileID{Start,Continue}Ranges` (the D137051/P3658R1 math-identifier profile), zero in the C++11–C++20 `C11AllowedIDCharRanges` whitelist. The U1@17.0 set stayed out of identifier space *after* the UCD moved under it. | U§7.1 can strengthen its claim: the partition is verified at 17.0 **and** holds against a 18.0 identifier set, which is the version-skew case a real implementation actually faces (a compiler updates its XID tables on Unicode's schedule while the frozen operator list does not move). Worth one sentence in U§7.1 and a note in U§4's "immutable versus stable" — the paper's strongest empirical answer to "what happens when Unicode updates?". |
| DEV-U03 | U02 | U§5 predicate 5 (the named exclusion list) | The exclusion list is given as prose: "∂ ∇ ∞", then "U+2212 −, U+2215 ∕ and U+2044 ⁄, U+2217 ∗, U+2223 ∣, U+2236 ∶, U+22C5 ⋅ **and the middle-dot family**, U+2264/U+2265 ≤ ≥ and … ⇐ ⇒ ⇔", then "anything with emoji presentation". | An implementation must enumerate it, and three things had to be decided to do that. (a) "The middle-dot family" is not a UCD family: inside the U1 blocks it resolves to exactly **U+2219 ∙ BULLET OPERATOR** and **U+22C5 ⋅ DOT OPERATOR** — U+00B7 MIDDLE DOT itself is **not Pattern_Syntax** (Unicode withheld it precisely because it is used *in identifiers*, e.g. Catalan), so it was never a candidate. (b) **U+2044 ⁄ FRACTION SLASH is not in the U1 blocks** (it is U+2044, the blocks start at U+2190), so it already fails predicate 3; listing it under predicate 5 is harmless but misleading — of the 16 named exclusions it is the only one that would not otherwise have qualified. (c) U§8 wants the exclusions to carry the token they ape, but the list assigns none per character; U02 assigned them: − → `-`, ∕ ⁄ → `/`, ∗ → `*`, ∣ → `|`, ∶ → `:`, ∙ ⋅ → `.` (they are dot-shaped; the *visual* confusion is with `.`, not with the `*` their mathematics means), ≤ ⇐ → `<=`, ≥ → `>=`, ⇒ → `=>`, ⇔ → `<=>` (C++20 has a token that shape). The emoji-presentation exclusion resolves to **12** code points inside the blocks (⌚ ⌛ ⏩ ⏪ ⏫ ⏬ ⏰ ⏳ ⬛ ⬜ ⭐ ⭕). | Replace U§5 predicate 5's prose with the enumerated 16 + a pointer to the 12 emoji code points, each with its reason and (for a confusable) the token it apes — i.e. print the generated `ExcludedOperatorChars` table in the paper. Drop U+2044 from predicate 5 or annotate it "also fails predicate 3"; say "U+2219 and U+22C5" instead of "the middle-dot family", and note *why* U+00B7 cannot appear (not Pattern_Syntax — it is an identifier character), which is a small independent piece of evidence for U10. |
| DEV-U04 | U06 | U§8 "Clang — *The hard part — `DeclarationName`*" | "Overloaded operators are `CXXOperatorName` over the closed `OverloadedOperatorKind` enum… User operators need a new `DeclarationName` kind carrying the code point. The precedent is **`CXXLiteralOperatorName`**… This is a real cost — DeclarationName plumbing fans out — but it is a *worked* precedent, not terra incognita." | **The precedent held exactly, and the cost is smaller than the sentence implies — but the sharp edge is somewhere else entirely.** Measured: **33** switch sites over `DeclarationName::NameKind` across 20 files; the whole step is **21 files, +436/−1 lines**, of which **19 files / +249 lines** are production code and 186 lines are the new unittest. `CXXLiteralOperatorIdName`'s shape transplants almost line for line. What the sketch does not say: (a) the new kind is not a *choice* — the inline 3-bit `StoredNameKind` space is **completely full** (all eight values 0–7 taken), so any new kind is *forced* through `DeclarationNameExtra`; the literal-operator route is the only route. (b) `DeclarationNameExtra::ExtraKind` **cannot be appended to**: the single field `ExtraKindOrNumArgs` encodes an N-argument Objective-C selector as `ObjCMultiArgSelector + N`, and `getKind()` clamps every value ≥ `ObjCMultiArgSelector` back to it, so appending `CXXUserOperatorName` after it would silently misclassify every multi-keyword selector. It must be *inserted before* `ObjCMultiArgSelector`, renumbering `ExtraKind` 3→4 and `NameKind::ObjCMultiArgSelector` 11→12. (c) One of the 33 sites is **generated**, from `clang/include/clang/AST/PropertiesBase.td` into `AbstractBasicReader/Writer.inc` — it is not greppable as C++ and only the `-Wswitch` warning finds it. | U§8's `DeclarationName` paragraph should quantify rather than hedge: "a real cost" becomes "~250 lines across 19 files and 33 switch sites, one of them TableGen-generated" — a number the paper can defend, and small enough to be an argument *for* the design rather than a caveat. Then replace the "worked precedent" reassurance with the real finding: the operator-name space is not merely closed, it is **packed against Objective-C's variable-length selector encoding**, so opening it costs an enum renumbering in a shared header rather than a new enumerator. That is the sentence a committee reader wants — it says exactly how much of the difficulty is inherent to open-ended operator names (little) and how much is an accident of one compiler's bit-packing (most of it), and it is the kind of evidence GCC's `ansi_opname` half of U§8 should be measured against in the same units. |
| DEV-U05 | U07 | U§8 "Clang" bullet list; U§6's "parsing is the *easy* part of this feature, easier even than backtick"; U§7 "Declaring" | U§8's three Clang bullets are *Lexer*, *Parser* ("the `prec::Level` introduced for backtick serves as-is; a `tok::user_operator` case joins `tok::backtick` in `ParseRHSOfBinaryExpression`, and a case in `ParseCastExpression` handles the prefix form") and *the hard part — `DeclarationName`*. U§7 gives the declaring side one sentence: "*operator-function-id* grows one production… Everything downstream is the existing machinery." | **The headline claim holds — and the omitted half is now measured.** U§8's Parser bullet describes only *expression* parsing (U11/U12); the *declaring* side, which is where `operator⊞` becomes a name at all, is a separate and slightly larger piece of parser work: **8 production files, +89/−5 lines**, namely a new `UnqualifiedIdKind` with its payload and setter, one arm in `ParseUnqualifiedIdOperator`, one arm in `Sema::GetNameFromUnqualifiedId`, and **9 peer sites** that had to learn the kind — four template-id paths in `ParseExprCXX.cpp`, `Sema::isTemplateName`, and four `UnqualifiedIdKind` switches in `SemaDecl.cpp`/`SemaType.cpp`/`SemaDeclCXX.cpp` (all exhaustive, so `-Wswitch` found them; the build is warning-clean). Two findings inside that: (a) **tentative parsing needed a peer change the design does not anticipate.** `Parser::TryParseOperatorId` handles `operator new/delete`, the `OperatorKinds.def` punctuators, `()`, `[]`, a literal-operator-id, and *otherwise assumes a conversion-type-id follows*; a `tok::user_operator` fell through to that loop, found no decl-specifier, and returned `TPResult::Error`, so an ambiguous statement such as `S operator⊛(S, S);` was re-parsed as an expression and rejected. One four-line case fixes it. The backtick track needed a peer change in the *same file* at its S08, for an unrelated reason — so "tentative parsing has to be told about any new declarator-id token" is a two-for-two result across the two features, not a coincidence. (b) `TemplateIdAnnotation` has no slot for a code point, exactly as it has none for a literal-operator suffix (the pre-existing `// FIXME: Store name for literal operator too.`), so `operator⊞<T>` parses and resolves through the `TemplateName` while the annotation carries `nullptr`/`OO_None`. Upstream's one-line `OpKind` expression also *reads the wrong union member* for a literal-operator-id; U07 had to make that read kind-checked rather than inherit the bug for a `uint32_t` payload. | Split U§8's Parser bullet in two — *declaring* and *using* — and give the declaring half the measurement (~90 lines, 8 files, one new `UnqualifiedId` kind, 9 peer sites, all compiler-found) next to U§7's "grows one production". It supports U§6's claim rather than undercutting it: the parse cost really is small, and it is *smaller than the `DeclarationName` cost* (DEV-U04's ~250 lines / 33 sites), which is the ordering the design predicts. Then add the tentative-parsing sentence as a portable implementation note — "a compiler that disambiguates declarations from expressions by trial parse must teach that path the new token too; both Clang prototypes needed it" — because it is the one place the declaring side is *not* just "the existing machinery", and GCC's `cp_parser_*` tentative machinery will face the same question. |
