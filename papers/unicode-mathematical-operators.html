1. Abstractsource

I propose adding the ability to declare user defined operators, such as operator⊞ , allowing users to write a ⊞ b. The list of allowed operators is drawn from the mathematical operators described in Unicode Technical Report #25, Unicode Support for Mathematics (Beeton, Freytag, and Sargent III 2017), with confusables removed. The operators are otherwise normal functions, found by ordinary lookup rules and ordinary overload resolution. 

constexpr int operator⊞(int a, int b) { return a + b; }
static_assert(5 ⊞ 7 == 12);

Matrix operator⊗(Matrix const&, Matrix const&);
a ⊗ b ⊗ c                               // operator⊗(operator⊗(a, b), c)

Vec operator⊖(Vec const&);              // one parameter: unary prefix
⊖v                                      // operator⊖(v)

4. The designsource

Recognize the mathematical symbols that are not identifier as possible C++ operators when they appear in operator position. Since they are disjoint from identifiers there is no ambiguity. Defer the meaning of the expression to name lookup and overload resolution. For the operators assign a fixed precedence and associativity so that parsing does not need to take into account declarations.

4.1. x ⊞ y is the callsource

The form x ⊞ y desugars to operator ⊞(x,y) and everything else follows from that. x ⊞ y is operator⊞(x, y) ⊖x is operator⊖(x) and the member forms are x.operator⊞(y) and x.operator⊖().

4.2. What this paper changessource

An operator-function-id may be operator followed by a user-operator token — a single non-ASCII code point drawn from an enumerated set. Such a function is an ordinary free or member function.

One precedence level
A user-operator token after a complete operand is a binary operator at the user-infix level (the highest binary level, tighter than *, looser than the unary operators), left-associative, with cast-expression operands. Every user-introduced infix operator binds at that one strength, and there is no table.
No fixity declarations
Precedence and associativity are fixed.
Position decides fixity at the use
Operand position is prefix, post-operand is infix. No lookahead or whitespace rule. No consultation of what declarations are visible during parsing.
Arity decides the form at the declaration, and does not filter uses
Two parameters, or one as a member, is infix; one parameter, or none as a member, is prefix. The same convention as operator-().
No built-in candidates
There is no built-in meaning to protect, so nothing adds any. p ⊞ n on int* is a no-viable-overload error.
Candidates are assembled as for an existing overloaded operator
member and non-member together in one set, with ADL.
No postfix form, and no fold operator
Fold is not precluded, but not proposed. Postfix is unusual in math notation, and is also not proposed.

4.3. Design Constraintssource

  1. The operator set is disjoint from the identfier character set.
  2. The list is derived from Unicode recommendations.

4.4. Relation to D4307R2

Infix named operators (Downey 2026) are a disjoint proposal. The only shared bit is the proposed user-infix level for precedence.

5. The token setsource

5.1. Deriving itsource

UAX #31 defines R3c, "Operator Identifiers" — introduced by §4.2.1, "User-Defined Operators" — as operator syntax over the characters with the Pattern_Syntax property. C++23 already references UAX #31 normatively for identifiers (Downey et al. 2021), so the citation is the same shape to the same document.

This paper pins UAX #31 at revision 43 (Davis and Leroy 2025), the revision that goes with Unicode 17.0, and the derivation below runs against UCD 17.0 (The Unicode Consortium 2025). Revision 45 (Davis and Leroy 2026), for Unicode 18.0, was published on 2026-09-01, while I was working on this paper. There is no particular reason not to adopt Unicode 18, but because code points can be added to the set we must set a baseline for portable code.

R3c does not hand us a usable set directly. Pattern_Syntax includes the ASCII operator characters, every one of which is already a token, a token prefix, or blocked by adjacency. The usable pool is Pattern_Syntax minus ASCII.

A code point is a user-operator token if all of:

  1. it has Pattern_Syntax;
  2. it is outside ASCII;
  3. it lies in the mathematical and arrow blocks (U+2190–21FF, U+2200–22FF, U+2300–23FF, U+27C0–27EF, U+27F0–27FF, U+2900–297F, U+2980–29FF, U+2A00–2AFF, U+2B00–2BFF);
  4. its General_Category is Sm or So, which excludes the paired brackets (Ps/Pe) as delimiters worth leaving unspent;
  5. it is not on the exclusion list below.

Applied once against UCD 17.0, that yields 1,381 code points in 32 contiguous ranges. The lexer's table is 256 bytes and one binary search, on the non-ASCII path both compilers already walk for extended identifiers. The cost is very small.

This paper proposes to list the allowed code point table explicitly with the algorithm as non-normative.

5.2. Immutable is not closedsource

An immutable property in Unicode means that an assigned code point will neve gain or lose that property. However, that does not mean that newly asinged code points could not be given the property. In particular this means that confusability analysis can not be carried out in advance and must be performed after code point assignment. This is the reason not to just apply the algorithm blindly.

5.4. Spelling: the glyph and the UCNsource

A universal-character-name designating a user-operator code point (including the C++23 named form) forms that operator token. operator⊞, operator\u229E and operator\N{SQUARED PLUS} are the same declaration. Declare with one, define with another, use with a third, they are emitted identically. a \N{CIRCLED TIMES} b is a ⊗ b.

6. Placement in Grammarsource

6.1. One level for all user-introduced infixsource

user-infix-expression:
    cast-expression
    user-infix-expression user-operator cast-expression

unary-expression:
    ...
    user-operator cast-expression

Binary user operators occupy one precedence level: the highest binary level, tighter than * and looser than the unary operators, left-associative, with cast-expression operands. That is the user-infix level, and it is meant to serve all user-introduced infix syntax: it is the same level D4307R2 introduces for the backtick operator.

The precedence rules mean that -a ⊞ -b is operator⊞(-a, -b). 

-a ⊞ -b            // operator⊞(-a, -b)
a * b ⊞ c          // a * operator⊞(b, c)
a ⊞ b ⊗ c          // operator⊗(operator⊞(a, b), c)
a ⊞ ⊖b             // operator⊞(a, operator⊖(b))
⊖a ⊞ 2 * ⊖b        // (operator⊖(a) ⊞ 2) * operator⊖(b)

6.2. Prefix, and how position decidessource

Arity determines at the declaraion. In use, it is purely positional. Post-operand is infix, in operand position it is prefix. There is no lookahead or whitespace sensitivity.

6.3. Postfix, and why notsource

operator++ in prefix form is parsed as a cast-expression, in postfix in postfix-suffix, and ++ has no infix form. This restriction is not available for user defined operators without somehow pre-classifying them, which would mean assinging meaning to them. That is not possible as different fields have already ambiguated them.

6.4. Fold expressionssource

A user operator is not a fold operator: (... ⊞ N) is ill-formed.

This is primarily because the existing implementations do not provide a mechanism to extend the fold-expression node beyond the current fixed and closed set. Adding the capability is certainly possible if there is real demand, but should be a separate paper, possibly considering other monoidal operations.

7. Declaring, looking up, desugaringsource

7.1. Restrictions on Operatorssource

[over.oper.general] imposes five restrictions on an operator function. A user operator inherits only one of them.

class-or-enum parameter
does not apply. The rule protects a built-in meaning, and there is none. constexpr int operator⊞(int, int) is legal, and 5 ⊞ 7 finding it is the motivating case.
no default arguments
does not apply.
not variadic
does not apply, likewise.
the fixed arity table
has no entry to consult, so the prefix/infix rule is written out.
not a static member

kept, and kept as a choice, because the arity rule does not exclude it.

That rule counts operands, so static S operator⊞(S, S) has two and would be accepted; an implementation must reject it deliberately. The reason is the desugaring: x ⊞ y is defined to mean exactly one of two spellings, operator⊞(x, y) or x.operator⊞(y), and a static member names neither. On a static member, x.operator⊞(y) is legal C++ but discards the object expression and passes one argument to a two-parameter function.

Everything else is ordinary: templates, constexpr, = delete, member and non-member, explicit object parameters.

Dropping [over.oper.general] paragraph 10 has a visible consequence. Given only constexpr int operator⊟(int a, int b = 1), the prefix use ⊟5 is accepted and calls it through the default argument, and adding a genuine prefix overload makes ⊟5 ambiguous in the ordinary way. Filtering candidates by declared arity would fix it. However, it would break the desugaring equivalence below, on which the whole design rests: ⊟5 is operator⊟(5). So arity selects the form for declarations, and does not filter uses.

7.2. One candidate set, and no built-in candidatessource

x ⊞ y assembles member candidates from the left operand's class and non-member candidates from unqualified lookup and ADL, ranked together in one set.

The normative requirement is that the operator form finds what the explicit call finds: 

static_assert(__is_same(decltype(x ⊘ y), decltype(operator⊘(x, y))));

8. One level, and no fixity declarationssource

Precedence and associativity are fixed by this paper, at one level, and neither can be declared. Of the rules fixed above this is the one most likely to be argued, so the two alternatives are answered here: a declared fixity is an ODR factory, and a derived one has nothing in Unicode to derive from.

A declared precedence is a semantic property that must travel with the name across headers, modules and translation units. Two translation units disagreeing about a ⊕ b ⊗ c is an ODR factory, and the parse of an expression comes to depend on which imports are visible: Haskell's fixity-import problem, and Swift's precedencegroup conflicts (“The Swift Programming Language: Advanced Operators,” n.d.). With fixity settled by the standard, the parse of an expression depends on nothing but the expression. Only the meaning of operator⊞ travels, and that is ordinary lookup.

9. Implementation experiencesource

This proposal has been implemented in Clang against 23 and the changes ported forward to trunk. There were no particular surprises or difficulty once a new expression node was added.

9.2. Mangling and ABIsource

The prototype mangles through the Itanium ABI's existing vendor-extended operator production, which works today, demangles with existing tools, and needs no ABI change. However, it would be better to have the Itanium ABI group provide first-class production keyed by code point and carrying a fixity marker.

The Microsoft ABI has no production for such operators at all, and I declined to invent one at let it escape.

9.3. Formattingsource

clang-format required about forty lines across three files: no new token type, no annotator state, no custom spacing rule, no custom break rule and no style option. A user operator is annotated as a binary or unary operator by position, with no delimiter pairing and no break-suppression rules, and the existing overloaded-operator handling rewrites the annotation after operator with no new rule, so operator ⊞ canonicalizes to operator⊞ under the same option that governs operator +. It also honours BreakBeforeBinaryOperators, which a delimiter-pair syntax structurally cannot.

10. Wordingsource

The following wording is pro forma. It is intended to make the grammar change concrete; it is not offered as final CWG wording. Wording is relative to the current working draft.

10.1. [lex.operators]source

Add user-operator as an alternative of operator-or-punctuator in [lex.operators]: 

user-operator:
    one of the characters in Table X, User-operator characters

Table X will contain the frozen enumeration of 1,381 code points described in 5. A universal-character-name designating one of those characters forms the same token by the existing translation rules.

10.2. [expr.unary.general]source

Add an alternative to unary-expression in [expr.unary.general]: 

unary-expression:
    ...
    user-operator cast-expression

10.3. [expr.mptr.oper]source

Modify the grammar of [expr.mptr.oper] paragraph 1: 

pm-expression:
    cast-expression user-infix-expression
    pm-expression .* cast-expression user-infix-expression
    pm-expression ->* cast-expression user-infix-expression

10.4. [expr.user] (new subclause)source

Insert a new subclause between [expr.cast] and [expr.mptr.oper]:

User-defined operators [expr.user]source

user-infix-expression:
    cast-expression
    user-infix-expression user-operator cast-expression

10.5. [over.oper.general]source

Modify the operator-function-id grammar in [over.oper.general]: 

operator-function-id:
    operator operator
    operator user-operator

Add after the grammar:

An operator function whose operator-function-id contains a user-operator is a user-operator function.

Modify the first sentence of [over.oper.general] paragraph 7:

An operator function other than a user-operator function shall have at least one function parameter or implicit object parameter whose type is a class, a reference to a class, an enumeration, or a reference to an enumeration.

Modify [over.oper.general] paragraph 10:

An operator function other than a user-operator function cannot have default arguments, except where explicitly stated below. Operator functions other than user-operator functions cannot have more or fewer parameters than the number required for the corresponding operator, as described in the rest of [over.oper].

Modify the first sentence of [over.match.oper] paragraph 1:

Unless the operator is a user-operator, if If no operand of an operator in an expression has a type that is a class or an enumeration, the operator is assumed to be a built-in operator and interpreted according to [expr.compound].

Modify the first and last sentences of [over.match.oper] paragraph 2:

If the operator is a user-operator or either operand has a type that is a class or an enumeration, a user-defined operator function can be declared that implements this operator or a user-defined conversion can be necessary to convert the operand to a type that is appropriate for a built-in operator. Modify the built-in-candidate bullet of [over.match.oper] paragraph 3:

For the operator ,, the unary operator &, or the operator ->, or a user-operator, the built-in candidates set is empty.

10.7. [over.unary] and [over.binary]source

In [over.unary], extend the definition of a prefix unary operator function to include a function named by a user-operator in the added unary-expression production. In [over.binary], extend the definition of a binary operator function to include a function named by a user-operator in a user-infix-expression. The existing transformations to member and non-member function-call notation then apply unchanged.

Annex A ([gram]) is updated mechanically to match.
